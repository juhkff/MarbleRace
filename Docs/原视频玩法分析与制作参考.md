# 原视频玩法分析与制作参考

> 项目：MarbleRace · UE 5.8 · 文档版本：v1.1  
> **来源纠正（用户补充）**：原视频基于 **Marble Race Simple** 的游戏画面，角色头像、姓名、BGM 等通过后期剪辑添加；当角色对应的球成为第一时，切换该角色的音乐。本文“画面确认”仅确认视频成片中的表现，不代表原游戏原生支持。**本项目要求将这些后期呈现直接内置为实时功能。**具体需求见[《角色呈现与领跑音乐系统》](<角色呈现与领跑音乐系统.md>)。
> 用途：统一玩法理解、拆分后续制作任务、制定验收标准。本文不是原游戏源码分析，也不代表当前项目已经实现全部功能。

## 1. 参考来源与观察范围

- 原视频：[Bilibili BV1nAEw69EWV](https://www.bilibili.com/video/BV1nAEw69EWV/)。
- 本次获取的视频流时长约 **14 分 31 秒**，分辨率 **388 × 854**；这是分析用的低分辨率版本，不是原始画质。
- 观察方法：全片约每 30 秒抽样概览；随后对开局、运动机关、中段分流、首批冲线和结算重新按明确时间点取帧。末段反弹行为使用 **223–228.5 秒、间隔 0.5 秒**的序列交叉检查。
- 本文时间码均指**视频播放时间**，不等于游戏内计时。录像可能包含开场效果、时间偏移或剪辑，不能直接据此反推模拟时长或物理速度。
- 本次分析的是画面，没有对音轨做判断；音乐、音效和语音不列为已确认功能。
- 证据图来自参考视频，仅供内部分析与制作核对；正式发行应使用自制或获授权的头像、素材，不直接移植视频水印或角色图片。

### 证据标记

| 标记 | 含义 |
|---|---|
| **确认** | 画面或多个时序样本直接支持 |
| **推断** | 行为支持此解释，但不能确定内部机制 |
| **建议** | 为本项目提出的实现方案，不是视频事实 |
| **待核实** | 当前画面不足以确定，不应直接写成硬性规则 |

## 2. 核心结论：我们实际要做什么

参考成片由 **Marble Race Simple 的弹珠竞速画面 + 后期角色化包装**构成：大量选手同时出发，在纵向二维赛道中受重力、碰撞和运动机关影响，逐渐拉开差距，按到达终点的先后顺序产生名次和用时；头像、姓名及领跑者主题音乐等来自后期制作（用户说明）。

**本项目目标是将两层合并为一个实时运行的多人角色弹珠竞速／观赛游戏**，直接生成带角色包装和动态 BGM 的画面，不依赖录制后再逐球贴头像、加名字或剪音乐。

核心体验不是操控某一颗球跳跃闯关，而是：

> 认领或关注一个选手 → 观看拥挤混战 → 被机关暂时困住或突然脱困 → 发生反超 → 冲线得到名次。

**画面未显示 WASD、摇杆或主动技能操作。**这支持将当前项目设计为自动比赛，但不能据此证明原游戏没有任何赛前配置或隐藏交互。

### 最重要的三个修正

1. **14 分钟不是 14 分钟长度的新赛道。**约 4 分钟后，画面大量停留在相同的末段机关，等待不同选手完赛；后半段的体验主要来自选手差距和反弹阻滞。
2. **关卡不能全做成静态坡道。**原片有旋转圆弧、转动拨板、强反弹平台、周期运动的红色构件。只做重力下落的短斜坡链不能还原其节奏。
3. **识别系统是核心玩法的一部分。**角色头像、姓名、彩色尾迹和冲线提示让观众能追踪选手；视频不是以国旗球为主。

## 3. 一场比赛的流程

| 阶段 | 观察到的表现 | 后续制作目标 |
|---|---|---|
| 集结 | 大量带头像和姓名的圆形选手聚集在黑色环形出发区 | 生成参赛者、摆放初始位置、冻结或围挡选手 |
| 倒计时 | 开局可见倒计时数字和 `GO!` | 使用统一比赛时钟；倒计时结束后统一释放 |
| 群体下落 | 选手进入钉阵，碰撞后分散；姓名高度重叠 | 保留群体混战，避免永久堵塞 |
| 分段竞速 | 先后通过闸口、旋转结构、折返通道、分流区等 | 通过不同机制产生可逆的领先优势 |
| 终点前争夺 | 青色平台上持续反弹，红杆周期变化；选手可能反复回到上方 | 让完赛时间取决于碰撞轨迹与机关时机，而非单次自由落体 |
| 陆续冲线 | 黑白格横线、`1st:`／`2nd:` 等名次提示、已完赛选手在下方聚集 | 每个选手只记录一次成绩，已完赛者与赛道逻辑分离 |
| 结果展示 | “比赛结果”“时间”、排序名单、“继续”按钮 | 显示名次、头像／姓名、用时；提供下一次比赛入口 |

### 人数与时间的可确认范围

- 开局明显是数十名选手，而不是单球测试。
- 结算页可见到 **第 53 名**，因此至少有 53 个成绩条目；不能仅凭截图认定系统最大人数就是 53。
- 可读到的前列成绩包括第一名“五条悟” **03:56.33**、第二名“L” **03:56.81**，两者仅差 **0.48 秒**。
- 后列成绩达到约 12 分钟以上，说明队伍被显著拉开；不建议初版照搬漫长等待，先完成玩法闭环，再调节节目节奏。
- “继续”按钮之后的实际行为没有在本次观察中确认，不能直接写成“自动生成下一张随机地图”。

## 4. 赛道顺序与机关拆解

以下为本段录像中观察到的顺序，不代表原游戏只有这些模块。时间区间是查证入口，不是精确模块起止边界；镜头会跟随不同位置的选手。

### A. 环形出发区 → 密集钉阵（约 00:00–00:12）

**确认**
- 多名头像球先在黑色环形区域内聚集，倒计时后整体释放。
- 下方是错列黑色圆钉，两侧有向内的斜向导流结构。
- 钉阵底部存在红色短条与出口，选手通过后进入下一段。

**作用**
- 打散初始队形，产生第一轮领先者。
- 密集碰撞让开局具有混战感，而不是所有球按相同轨迹排队。

**建议**
- 首版先做固定圆钉，不因单张图就认定侧边短杆也在摆动。
- 用球直径 `D` 统一定义间隙；希望所有球自然通过的出口应大于 `D`，不要意外制造死锁。
- 释放装置和容器要独立，不能通过删除全部碰撞体来同时破坏赛道。

[开局时序证据](<Reference/start-sheet.jpg>)

### B. 多层窄口／横向杆件段（约 00:12–00:22）

**确认**
- 两侧伸出的多层黑色横杆之间留有通路，部分端头为紫色。
- 同段出现红色侧边和黑色三角构件。
- 不同时刻可见的端头／通路布局存在变化迹象。

**推断与待核实**
- 可能通过杆件运动改变通行窗口；目前不足以确定每根杆的运动轴、周期、相位。
- 红色、紫色或三角形外观本身不代表伤害、淘汰或技能效果。

**建议**
- 将此模块命名为“周期闸口候选”，不要现在就固定成伤害机关。
- 正式制作前，以同一层杆件为参照连续跟踪一周期，确认是伸缩、平移还是其他运动。

### C. 第一组旋转圆弧／螺旋结构（约 00:22–00:30）

**确认**
- 多层黑色圆弧围成回旋路线，外圈存在缺口。
- 25、27、29 秒的圆弧朝向变化，选手在其中移动并从下方离开。

**作用**
- 暂时容纳选手，利用旋转相位和缺口产生放行时机。
- 领先者可能滞留，为后来者追赶创造机会。

**建议**
- 圆弧与直墙不能只用一个整体凸碰撞包围；需要分段碰撞保留通路。
- 将半径、弧长、缺口角度、角速度、方向作为可编辑参数。
- 当前取帧不能证明每层独立旋转，先验证整体旋转版本，再按证据细分。

### D. 圆底腔体与旋转拨板（约 00:30–00:50）

**确认**
- 腔体底部为弧形，上方有入口／出口结构。
- 35、38、41 秒，内部黑色长拨板的角度明显变化。
- 选手不只是下落，也会被带起、抛向高处。

**作用**
- 主动向球提供动量，使重力竞速出现回升与重复尝试。

**建议**
- 拨板应真实参与碰撞，而不是只播放旋转视觉动画。
- 必须限制速度与卡夹风险；需要测试球位于拨板端头和墙角时的行为。

### E. 曲折腔体与左侧格栅式结构（约 00:50–01:15）

**确认**
- 上部收口后进入弯曲通道，下部有圆底空间、凸柱和左侧多个方格状开口。
- 同一选手在多个时刻处于左侧格栅的不同高度，其他选手进入下部空间。

**待核实**
- 格栅究竟是升降、旋转框架还是固定结构配合内部运动，当前证据不足。
- 不能直接将其解释为传送门或自动电梯。

**建议**
- 先做灰盒并补充连续观察；这是高歧义模块，放在基础闭环完成之后。

[旋转与腔体时序证据](<Reference/mechanisms-sheet.jpg>)

### F. 密集折返斜通道（约 01:15–02:25）

**确认**
- 连续黑色楔形墙把通路压成左右折返的浅蓝细带。
- 选手沿多层折返通道下降；局部可见红色构件。

**作用**
- 延长路径、控制速度、使不同球的碰撞误差逐层累积。

**建议**
- 与当前“宽阔空间中六块孤立斜坡”的原型区分：原片更像受上下边界约束的连续折返通道。
- 先保证狭窄通道能稳定通过，再增加特殊构件；不要把碰撞缝隙当作设计难度。

### G. 第二组大型多层圆弧（约 02:25–03:00）

**确认**
- 再次出现大型多层圆弧结构，多个选手在其中汇聚。
- 150、160、170、175 秒的开口方向变化明显。

**作用**
- 将领先小组重新聚在一起；再次形成等待相位和集中释放。

**建议**
- 复用 C 模块，但使用不同半径、层数与旋转参数，避免重复造轮子。

### H. 双列小模块组合／分流区（约 03:00–03:25）

**确认**
- 画面左右并排展示钉阵、圆底容器、小斜坡和青色台阶等小区域。
- 不同选手处于不同小区域，区域边缘可见红、绿、蓝等颜色条。
- 选手最终继续向下进入共同的后续赛段。

**待核实**
- 颜色块是否是传送入口、切换触发器、弹性表面或纯视觉标识，不能仅凭图确认。
- 不能把并排小模块误写成“多个玩家分屏独立比赛”。

**建议**
- 首版可做实体分流后汇合，避免在未确认规则时加入传送。
- 用明确入口／出口标识保证进度计算不会因分支而出错。

### I. 红色长杆交叉区（约 03:25–03:32）

**确认**
- 多层黑色平台附近出现长红杆；205 秒可见明显交叉的斜向结构。

**待核实**
- 该段观察窗口较短，运动方式、速度和伤害规则尚不能可靠判断。

**建议**
- 作为后续运动杆件模块预留，不要直接把它写成“杀死球的激光”。

[中段与分流区证据](<Reference/middle-sheet.jpg>)

### J. 强反弹平台与周期红杆（约 03:30 起，后半程主要停留区）

**确认**
- 多层黑色平台顶部有亮青色表面，左右交替留出口，底部有中央通道。
- 同一选手反复在平台之间弹起；223–228.5 秒序列可看到下降后重新上升、横向折返。
- 红色竖杆相对平台的伸出长度／位置随时间改变，有时仅露出短段，有时伸到上下层之间。
- 某些平台下方有黑色三角凸起；球不会因为画面出现三角形就必然消失。
- 多位选手陆续经过同一组末段结构，不是每位选手在一张新地图上比赛。

**推断**
- 青色顶面很可能标记高弹性或主动反弹表面；画面能确认强反弹，但不能区分高恢复系数与脚本冲量。
- 红杆改变运动路线或通行时机。是否还有特殊碰撞效果仍待核实。

**建议**
- 初版用普通碰撞和受控反弹二选一实现，避免“高恢复系数 + 每次碰撞额外加速”叠加导致无限增能。
- 为反弹设置目标速度或上限，使球能跨越障碍但不飞出赛道。
- 红杆的周期、振幅和相位可配置；周期运动基于比赛时钟，方便复测。
- 长时间无进展需要检测和记录；是否救援、重置或判定未完赛应由设计明确，而不是暗中传送。

[半秒间隔反弹证据](<Reference/bounce-sheet.jpg>)

### K. 黑白格终点与收集区（首批冲线约 04:05 附近，之后持续发生）

**确认**
- 黑白格横线跨越赛道，选手穿过后出现名次反馈。
- 下方可见已完赛选手聚集；比赛不会因第一名产生立即结束。
- 末尾出现排名与用时列表。

**建议**
- 将终点实现为跨越通路的触发区，不是阻挡球的实体横梁。
- 首次有效穿越后锁定名次与完赛时间；回弹再次穿越不能重复获奖。
- 已完赛球进入收集区或切换碰撞层，防止返回赛道干扰未完赛者。

## 5. 物理规则：哪些已知，哪些不能猜

| 项目 | 结论 | 制作处理 |
|---|---|---|
| 总体运动 | 确认总体向下，但局部明显向上反弹或被抛起 | 重力只是基础，还需动态机关和反弹 |
| 球之间碰撞 | 群体接触与分散支持存在相互作用，但无法读出参数 | 建议先启用球间碰撞，做密集场景测试 |
| 球体尺寸 | 画面会变焦，不宜据单帧认定球尺寸变化 | 用统一 `D` 作为设计尺度；不添加“变大技能” |
| 摩擦与弹性 | 无法由视频直接得到系数 | 用测试场调参，不标注为原版数值 |
| 三角形 | 能确认外形，不能确认伤害 | 默认障碍碰撞，伤害机制需独立证据 |
| 彩色条 | 能确认颜色与位置 | 不自动等同于弹簧、传送、加速或死亡 |
| 淘汰／复活 | 未发现足以确定统一规则的证据 | 初版不强加生命值与复活系统 |
| 随机性 | 结果有混战和不同轨迹 | 未确认随机种子或抽签；不能声称原版纯随机 |
| 球头像旋转 | 低清素材与运动使判定不稳定 | 可先保持头像朝镜头，物理自转与视觉分离 |

### 推荐的尺度与稳定性原则（不是原版参数）

- 以球直径 `D` 定义几何；普通出口可先试 `1.5D–2D`，再按拥堵情况收窄。
- 检查墙—钉、墙—拨板、坡道接缝的最小动态间隙，而不只检查静止截图。
- 对高速球启用连续碰撞检测；旋转机关还需要足够的碰撞精度和更新频率，CCD 不是万能修复。
- 曲线碰撞需要平滑衔接，防止球被分段凸起卡住。
- 调试时记录位置、速度、当前模块、最近进度变化时刻，区分正常等待与碰撞死锁。
- 不同帧率下允许细节轨迹不同，但不能出现系统性穿墙或无法结束比赛。

## 6. 视觉、镜头与信息呈现

### 6.1 视觉语言

**确认**
- 竖屏、近似平面侧视；浅蓝背景、大面积黑色轮廓。
- 弹珠使用角色头像圆形裁切，姓名紧邻球体；彩色尾迹用于表现运动轨迹与辨识选手。
- 背景有零星彩色小装饰；画面上还有深蓝灰横带，但其是否具有碰撞或触发功能未确认。
- 视频帧此前取色的背景主色约为 **sRGB #71D0FD**；压缩、截图和显示管线会带来偏差，应视为参考值而非绝对标准。

**本项目美术建议**
- 使用无光照材质，禁用球体投影；二维外观不要求放弃三维碰撞。
- 明确关闭不需要的 Bloom、暗角、景深、运动模糊等后处理；不要把屏幕边缘压暗误认为背景本身颜色不均。
- 不以“大幅提高自发光”代替色彩校准；曝光与色调映射应统一配置后再定调色板。
- 尾迹是有意的轨迹表现，不等同于球面高光或环境泛光。
- 角色头像选用自制／授权素材；不要将视频中现成角色图当作默认可商用资产。

### 6.2 镜头

**确认**
- 视野沿纵向赛道移动，不固定展示整张地图。
- 开场含明显的尺度变化；后续会展示领先者、小组和仍未完赛者。
- 第一批人完赛后，镜头继续展示后续选手，而不是一直停留在冠军身上。

**待核实**
- 自动跟随算法、手动选择目标、镜头切换触发条件无法由画面确定。
- 右下角可见眼睛样式图标，但其交互功能不能只凭图标推定。

**建议**
1. 赛道横向居中，镜头主要沿竖直方向移动。
2. 保留目标前方的观察空间，但允许跟随反弹向上移动，不能强制相机只向下滚动。
3. 默认关注领先的未完赛选手；当前目标完赛后切换到下一位未完赛者。
4. 相近选手可小范围缩放纳入画面；设置切换冷却，避免每次名次波动都抖动。
5. 提供观众手动锁定选手的扩展接口，但此功能属于建议，不是已确认原版功能。

### 6.3 UI

**优先复现的已确认内容**：倒计时、GO、姓名、头像、彩色尾迹、冲线名次、结果名单、用时、“继续”按钮。

**不要误认为原版已确认的内容**：实时常驻排行榜、选手能力面板、技能冷却、投注系统、国旗选择、赛事联网。

姓名高度重叠是视频的实际表现，但本项目可改进：仅突出关注者与近邻，其他姓名淡化／缩小。此改进应标注为自己的设计，不声称逐像素复刻。

## 7. 当前项目与参考玩法的差距

以下基于本轮已知项目状态与读取的 [GameMode 源码](<../Source/MarbleRace/Private/Race/MarbleRaceGameMode.cpp>)，不是对全部二进制资源的完整审计。

| 方面 | 当前原型 | 与参考的差距 |
|---|---|---|
| 基础运动 | 单球、重力、平面约束、已做 CCD 设置 | 缺少数十球同时参赛的稳定性验证 |
| 视觉 | 已有浅蓝背景、扁平材质、黑色轮廓 | 缺头像、名字、尾迹及统一后处理验收 |
| 赛道 | 钉阵、漏斗、六段斜坡、静态红块与尖刺、终点外观 | 主要是风格示意，不是原片完整几何与机制 |
| 机关 | 主要为静态构件 | 缺旋转圆弧、拨板、周期红杆、强反弹末段 |
| 比赛流程 | 进入运行后直接模拟 | 缺参赛者管理、倒计时、统一计时和完赛状态 |
| 镜头 | 源码取得第一个 `RaceMarble`，水平位置固定、平滑跟随高度 | 缺目标切换与多球观赛逻辑；源码状态不等于已核对的编译产物 |
| 终点 | 有黑白格与平台外观 | 尚未建立已验证的冲线判定、唯一排名与成绩表 |

**不要以“现有球能落到底部”作为玩法复刻完成标准。**

## 8. 推荐制作路线与验收

### P0：先完成一场可结束的比赛

内容：8–12 个可区分的参赛球、倒计时、短赛道、终点触发、名次／用时、收集区、结果与重开。

验收：
- 倒计时前无人提前出发；所有人共用同一起跑时刻。
- 每人有稳定 ID；同名不混淆记录。
- 同一个人只能获得一次成绩；结果严格按有效冲线顺序排列。
- 第一名产生后比赛继续，镜头能转向尚未完赛者。
- 重开清除旧成绩、尾迹、触发状态及残留球，不叠加旧比赛。

### P0.5：把角色包装与领跑音乐实时内置（核心需求）

内容：每球绑定角色配置（头像、姓名、主题曲）；角色头像与姓名实时跟随；根据路线进度识别领跑者，并自动切换其主题音乐。详见[系统需求与验收](<角色呈现与领跑音乐系统.md>)。

验收：
- A 被 B 超越并满足稳定判定后，无人工操作切换到 B 的音乐。
- 领先者不变不重复重启音乐；短时并列或碰撞抖动不造成碎片式切歌。
- 头像、姓名、音乐映射来自同一份角色配置，不能串角色。
- 冠军产生后的音乐规则明确，镜头目标与音乐目标相互独立。
- 直接录制运行画面即可获得角色与音乐呈现；不要求额外后期合成。自动导出视频不包含在本阶段内。

### P1：制作决定观感的运动机关

内容：旋转圆弧、拨板、反弹平台、周期红杆，先放在独立测试场，再组成短赛道。

验收：
- 球能被机关阻滞后重新放行，而不是永久卡死。
- 拨板能正确带起球；视觉位置与碰撞一致。
- 青色反弹区能产生可读轨迹，速度有上限。
- 红杆周期运动能改变路线，但不因极细缝隙持续夹死球。

### P2：按录像顺序拼出完整参考路线

内容：钉阵 → 窄口段 → 小圆弧 → 拨板腔体 → 曲折格栅区 → 折返通道 → 大圆弧 → 双列分流 → 红杆区 → 反弹末段 → 终点。

验收：
- 每段入口、出口、顺序明确；不意外绕过必经阶段。
- 所有分支能回到后续赛段。
- 尚未确认的模块先保留灰盒版本，补证据再定规则。

### P3：扩到数十人并完善观赛呈现

内容：约 50–60 球压力测试、头像姓名尾迹、目标切换、排名展示、竖屏布局。

验收：
- 用多种初始摆放重复测试；记录每段停留时间、完赛率、最长无进展时间。
- 分别测试 30／60／120 FPS 条件下的稳定性，不要求完全相同的物理结果。
- 背景、球、机关在静止与运动中均无不需要的光照渐变／投影。
- 头像／姓名／尾迹足以追踪选手；不因全员信息叠加完全遮住通路。

### P4：节奏与细节

内容：调整领先组与落后组差距、加结果动画、音效、可选救援规则等。

建议：短版先以数分钟以内完成为目标，再根据测试决定是否制作录像同款长时长观赛模式。不要通过故意制造物理死锁来延长比赛。

## 9. UE 实现拆分建议

以下是建议架构，不表示这些类已经存在。

| 模块 | 职责 |
|---|---|
| 比赛管理器 | Ready → Countdown → Racing → Results；统一时钟、参赛者与成绩 |
| 弹珠 Actor | 物理碰撞体、平面约束、头像显示、姓名、尾迹、状态 |
| 机关 Actor | 固定钉阵、旋转圆弧、拨板、周期杆、反弹面；暴露配置参数 |
| 赛段标记 | 记录路线进度，供相机选择目标与卡死检测使用 |
| 终点触发器 | 检查参赛状态和穿越方向，发出一次性完赛事件 |
| 观赛镜头 | 当前目标、下一目标选择、平滑移动、缩放边界 |
| 结果界面 | 名次、姓名／头像、用时、继续／重开 |
| 角色配置资产 | 稳定角色 ID、显示名、头像、主题音乐及播放起点 |
| 领跑判定器 | 基于路线进度生成稳定的领先者变更事件，与镜头解耦 |
| 音乐导演 | 监听领先者事件，加载并淡入淡出主题曲，处理冠军、暂停和重开 |

### 必要数据

- 选手：`RacerId`、显示名、头像、尾迹色、比赛状态、已通过赛段、完赛时刻、名次。
- 机关：中心、尺寸、转速或周期、振幅、相位、碰撞配置、调试标识。
- 比赛：参与人数、统一开始时刻、结束规则、最长等待策略。

### 排名不要只看高度

折返、反弹和分支会让高度反复变化。建议区分：

- **正式名次**：按有效终点事件排序，不再改变。
- **进行中进度**：已通过的赛段序号 + 当前赛段进度估计，用于镜头与临时显示。

同一物理步内多人冲线，需要明确稳定排序规则；可使用穿越插值时间，仍相同则按稳定 ID 排序。该规则是实现建议，不是从视频确认的原规则。

## 10. 后续补证据清单

1. 窄口段紫色端头的实际运动轨迹、周期、碰撞效果。
2. 曲折腔体左侧格栅的运动方式和选手进出路线。
3. 双列区颜色条是否对应传送或其他触发行为。
4. 红色长杆交叉区的完整运动周期。
5. 三角凸起、红色构件是否有非碰撞的惩罚效果。
6. 深蓝灰横带是否只是视觉分隔。
7. 镜头是否由用户操控，眼睛图标的实际用途。
8. 最后一名未完赛时是否有超时、救援或提前结算规则。
9. “继续”之后是重赛、下一地图还是返回菜单。
10. 用户已说明“领跑者变化时切换对应角色音乐”；音效、具体切歌时机、音乐起点与冠军产生后的策略仍需细化，不能声称已通过音轨验证。

## 11. 一句话制作原则

**先让多名可识别的选手完成一场有反超、有机关等待、有唯一排名的自动比赛，再扩展赛道与美术；不要用一串静态斜坡替代原片的核心玩法。**
